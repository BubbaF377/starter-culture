# StarterCulture

Working name: **StarterCulture** (styled as one word, no space). Brand/marketing website for StarterCulture, Christian's small AI-native software development studio, hosted at starterculturestudio.com.

## Working agreement

- Conversations about this project in the Claude desktop/Cowork app are planning-only: they get captured here as requirements, decisions, or open questions, not applied as direct code changes from that app.
- Actual code changes to this repo happen in Claude Code / VS Code sessions. An agent working from the desktop app should read this file for current context but not edit source files (e.g. anything under `src/`, `public/`, config files) unless Christian explicitly asks for that in the moment.

## Vision

A brand site that introduces StarterCulture as a small software development studio doing AI-first, AI-native development, and showcases the studio's products — currently Devkeep. The site should feel light, clean, and minimal, and give the studio a real home on the web that can grow to list future products, plus room for a company/team page and an eventual client portal.

    - **Auth architecture (decided):** Clients authenticate with Client ID + a one-time passcode checked by a Cloud Function, which then mints a **Firebase custom token** (uid `client_<CLIENTID>`, custom claim `client_id`). Firebase manages the resulting session and token refresh, replacing the Supabase-era hand-rolled `client_sessions` table and `x-client-session` header. Consequence: clients now *do* appear as Firebase Auth users, so "signed in" no longer means "is staff." **Staff are identified by a `staff: true` custom claim** (decided over an allowlist collection in Firestore), granted per team member with the Admin SDK script `functions/scripts/set-staff.mjs`. Firestore rules check that claim, never mere sign-in.
    - **Client session length:** 7 days, enforced in `firestore.rules` by checking the ID token's `auth_time`. After that, the portal's read is denied and the client is sent back to log in again.
    - **Firestore data model** (rules in `firestore.rules`, deployed with `firebase deploy`):
      - `clients/{clientId}` — the doc ID *is* the 6-character Client ID. Fields: `name`, `email`, `phone`, `project_name`, `content` (starts as "This is where we'll post information about your project."), `created_at`. Rules: staff can read/create/update; a client can read only their own doc (their `client_id` claim matches the doc ID).
      - `client_otp_codes/{clientId}` — `code_hash` (SHA-256; the code is never stored raw), `expires_at`, `attempts`. No rule grants any access — only Cloud Functions touch it, via the Admin SDK, which bypasses rules.
      - `personnel/{id}` — the About page's Builders/Advisors (see item 9): `name`, `title`, `section` (`builder`/`advisor`), `bio`, `linkedin_url`, `photo_url`, `sort_order`, `created_at`. Rules: public read; staff-only write.
    - **Cloud Functions** (`functions/`, TypeScript, 2nd-gen callable functions, region `us-central1` — same as the Firestore database, whose location is permanent). Deployed from the repo with `firebase deploy`, so the local source *is* the deployed source — the Supabase-era hand-sync between local files and a dashboard editor is gone. Callable functions handle CORS themselves.
      - `clientOtpRequest` — takes `{ clientId }`; if it matches a client, generates a 6-digit passcode, stores its hash (replacing any prior code, 10-minute expiry), and emails it via Resend. Always returns the same `{ ok: true }` whether or not the ID existed, so it can't be used to enumerate valid Client IDs.
      - `clientOtpVerify` — takes `{ clientId, code }`; checks the hash, expiry, and attempt count (max 5) in a transaction; on success deletes the code and returns `{ ok: true, token }` with the custom token.
      - No portal-content function — the portal reads Firestore directly under the rules.
    - **Email delivery: Resend**, sending from `otp@mail.starterculturestudio.com` — a dedicated subdomain (not the root domain) so its SPF/DKIM/DMARC records don't touch the existing Porkbun email-forwarding setup for `dev@starterculturestudio.com`. Domain is **Verified**. The API key is stored as the Cloud Functions secret `RESEND_API_KEY` (Sending-access only). A new Resend key is needed for Firebase, since the Supabase secret can't be read back.
    - **Client ID generation (decided):** the Client ID isn't chosen by hand — when the studio creates a new client record (via the Company/admin area below), the site generates the ID itself and hands it back to us to relay to the client. **Format: a 6-character alphanumeric code**, kept simple since the client has to type it in. Collisions are handled: the admin page creates the doc in a Firestore transaction that fails if that ID already exists, and retries with a fresh ID (up to 5 times).
