# StarterCulture

Working name: **StarterCulture** (styled as one word, no space). Brand/marketing website for StarterCulture, Christian's small AI-native software development studio, hosted at starterculturestudio.com.

## Working agreement

- Conversations about this project in the Claude desktop/Cowork app are planning-only: they get captured here as requirements, decisions, or open questions, not applied as direct code changes from that app.
- Actual code changes to this repo happen in Claude Code / VS Code sessions. An agent working from the desktop app should read this file for current context but not edit source files (e.g. anything under `src/`, `public/`, config files) unless Christian explicitly asks for that in the moment.

## Vision

A brand site that introduces StarterCulture as a small software development studio doing AI-first, AI-native development, and showcases the studio's products — starting with Devlore. The site should feel light, clean, and minimal, and give the studio a real home on the web that can grow to list future products, plus room for a company/team page and an eventual client portal.

9. **About page (`src/pages/_about.astro`)** — a fuller company narrative than the homepage's short studio blurb, plus a team section split into two subsections, in this order: **Builders** (the founding/equity team) and **Advisors** (domain experts consulted informally, not equity/founding). This isn't a rank hierarchy — Christian wants the studio flat and egalitarian (no President/VP/CEO-style titles, roughly equal pay) — Builders vs. Advisors is a factual distinction about relationship to the studio (founding + equity vs. informal advisory), not seniority.
    - **Per-person card (decided):** photo, name, title, short bio, and a LinkedIn icon placed near the name (not a separate line item lower on the card) linking to that person's profile — the LinkedIn link lets a visitor verify someone's background without the bio having to do all the work.

Whatever photo someone uploads now (casual or otherwise) is a placeholder — proper headshots are planned for later, swapped in the same way via re-upload.

    - **Spelling (decided): "Advisor"** (not "Adviser") — keep this spelling consistent across the section header and every individual title/reference.
    - Advisor slots currently planned: Architecture, Accounting, Legal. A Legal advisor hasn't been identified yet.
    - Content source: intended to be populated from the personnel records entered via the Company/admin area (see item 11) rather than hand-written per person in the page source — so adding/editing a Builder or Advisor doesn't require a source edit.

Drop the underscore (rename to `about.astro`) and add a footer link back in once Christian decides the page is ready to publish — conversations with prospective Builders/Advisors have happened, but no official terms (titles, equity) are finalized yet, so no real names should go live before that.
10. **Client Login (`src/pages/client-login.astro`) and Company Login (`src/pages/company-login.astro`)** — the login-gated flows for clients and for StarterCulture's own team. **UI is built and live-routable; auth is not wired up yet** (both pages carry a "🚧 Not yet connected — UI preview only" badge so real visitors aren't misled). The old `src/pages/_clients.astro` wireframe (non-functional email/password form) has been deleted — fully superseded by these two pages.
    - **Nav/footer Login dropdown — built.** A single **"Login"** entry in both the header nav and footer opens a dropdown with two options, **"Client Login"** and **"Company Login"**. Implemented as a plain `<details>`/`<summary>` element (no JS framework) in `src/components/Header.astro` and `Footer.astro`, styled via `.login-dropdown`/`.login-menu` in `src/styles/site.css`; footer's copy of the menu opens upward so it stays on-screen. A small shared script in `src/layouts/Layout.astro` closes any open dropdown on an outside click.
    - **Client Login page — UI built.** Landing copy: "This page is for StarterCulture clients. Log in here to see working models, documentation, and other materials for your project." Below it: a Client ID form which, on submit, currently just reveals a passcode-entry step client-side (a "← Use a different Client ID" link goes back) — no real lookup or OTP email happens yet.
    - **Decided login flow (still the target, not yet implemented):** (a) client enters their **Client ID** (an identifier StarterCulture issues per client — not their email); (b) on submit, we look up whether that ID exists in our client records; (c) if it exists, we email a one-time passcode to the email address on file for that client; (d) they're shown the passcode-entry step; (e) once the correct passcode is entered, they're authenticated and land on their client content area.
    - **Supabase project — created.** A **dedicated new Supabase project for this site** (decided against reusing the `perfect-stranger` project's instance, to avoid mixing two products' `auth.users`, email templates, and redirect-URL allowlists in one project): `starter-culture`, in the `BubbaF377's Org` organization, region Canada (Central) to match `perfect-stranger`. Project URL: `https://wklchodmfgmtsateuryy.supabase.co`. The publishable (anon-equivalent) key is safe to put in client-side site code; the secret key stays server-side-only (for a future Edge Function) and was deliberately never revealed/copied into any file. The database password generated at project creation was left masked and not recorded anywhere — not needed for the planned architecture (schema work goes through the dashboard's SQL Editor, not raw Postgres credentials); reset it via Database Settings first if direct Postgres/psql access is ever needed.
    - **Auth architecture (decided):** Client Login is **deliberately not Supabase Auth**. Clients never become rows in `auth.users` — they authenticate via Client ID + a one-time passcode verified by a server-side Edge Function, which issues its own short-lived session token. This is what keeps "Supabase's own user table is the list of valid company members" (item 11) literally true — only staff (Company Login, real Supabase Auth magic links) ever hold an authenticated Supabase session, so RLS policies can treat `to authenticated` as "is staff" with no separate allowlist table.
    - **Schema — built** (`supabase/migrations/0001_init.sql` and `0002_client_sessions.sql`, applied via the SQL Editor):
      - `clients` — `client_id` (unique 6-char code), `name`, `email`, `phone`, `project_name`, `content` (defaults to the "This is where we'll post information about your project" placeholder), `created_at`. RLS: staff (`authenticated`) can select/insert/update; deliberately no anon policy.
      - `client_otp_codes` — `client_id` (references `clients`), `code_hash` (the OTP is hashed, never stored raw), `expires_at`, `attempts` (rate-limiting), `created_at`. RLS enabled with **zero policies**, and deliberately left un-exposed in Data API settings too — only ever reached by Edge Functions over a direct Postgres connection (`SUPABASE_DB_URL`), never through the public REST surface.
      - `client_sessions` — session tokens issued after a successful OTP check: `client_id`, `token_hash` (token is hashed, never stored raw), `expires_at`, `created_at`. Same treatment as `client_otp_codes`: RLS with zero policies, unexposed in Data API.
      - `personnel` — the About page's Builders/Advisors table (see item 9): `name`, `title`, `section` (`builder`/`advisor`, checked), `bio`, `linkedin_url`, `photo_url`, `sort_order`, `created_at`. RLS: public `select` (`anon, authenticated`); `insert`/`update`/`delete` restricted to staff (`authenticated`).
      - **Data API exposed tables (decided):** `clients` and `personnel` are exposed (2 of 4 tables); `client_otp_codes` and `client_sessions` are intentionally left unexposed. "Automatically expose new tables" is off project-wide, so any future table needs the same explicit opt-in.
    - **Edge Functions — built and deployed** (via the dashboard's function editor; source also lives in `supabase/functions/` for version control, though the CLI isn't set up for deploys yet — see Open Questions):
      - `client-otp-request` — takes `{ client_id }`; if it matches a client, generates a 6-digit OTP, hashes it, stores it (replacing any prior code for that client, 10-minute expiry), and emails it via Resend. Always returns the same generic `{ ok: true }` regardless of whether the ID existed, so the endpoint can't be used to enumerate valid Client IDs.
      - `client-otp-verify` — takes `{ client_id, code }`; checks the stored hash, expiry (10 min), and attempt count (max 5, tracked via `client_otp_codes.attempts`), then on success deletes the OTP and issues a `client_sessions` row (7-day expiry) plus a random token returned to the caller.
      - `client-portal-content` — takes the session token via an **`x-client-session` header** (deliberately not `Authorization`, since that header is already claimed by Supabase's own JWT verification on the function — the publishable/anon key goes there instead) and returns that client's `project_name`/`content` if the session is valid and unexpired.
      - All three connect to Postgres directly via the `postgres` npm package using `SUPABASE_DB_URL` (a default Supabase secret), bypassing PostgREST entirely — consistent with `client_otp_codes`/`client_sessions` never being Data-API-exposed.
      - CORS is handled per-function (shared logic duplicated across the three deployed copies, since the dashboard editor deploys one function's files at a time rather than the whole `supabase/functions/` tree — the local `_shared/cors.ts` and `_shared/hash.ts` are the canonical source, kept in sync by hand for now).
    - **Email delivery: Resend**, via a `starter-culture-client-login` API key (Sending-access only) stored as the `RESEND_API_KEY` Supabase Function secret. Sends from `otp@mail.starterculturestudio.com` — a dedicated subdomain (not the root domain) so its SPF/DKIM/DMARC records don't touch the existing Porkbun email-forwarding setup for `dev@starterculturestudio.com`. **Domain verification was still pending (DNS just added) as of this writing** — check Resend's Domains page before relying on real email delivery; until verified, sends from that domain will fail.
    - **Client ID generation (decided):** the Client ID isn't chosen by hand — when the studio creates a new client record (via the Company/admin login below), the site generates the ID itself and hands it back to us to relay to the client. **Format: a 6-character alphanumeric code**, kept simple since the client has to type it in.
    - Behind the login, each client sees content StarterCulture uploads as work on their project progresses (e.g. working models, documentation) — exact content types and how the studio manages/uploads that content per client are still open (see below).
    - **Company Login page — UI built, not wired up.** Copy: "StarterCulture team members: sign in with your email to reach the admin area." An email form which, on submit, currently just reveals a "check your email" confirmation step client-side — no real magic-link email is sent yet. Unlike Client Login, this one doesn't need a custom Edge Function — Supabase Auth's own `signInWithOtp` (magic-link mode), called directly from the browser with the publishable key, is sufficient once wired up.
    - **Front-end wiring (not yet done):** `client-login.astro` and `company-login.astro` still only do the click-through placeholder UI described above — neither page actually calls the deployed Edge Functions or Supabase Auth yet.
11. **Company login / admin area** — a separate authenticated area for StarterCulture itself, reached via the "Company Login" option in the same Login dropdown as Client Login (see above). **Nothing in this item is built yet** — only the Company Login page's front-end UI (see item 10) exists so far; the admin area itself (forms, client list, personnel management) is still just planning.
    - **Auth mechanism (decided): Supabase email magic link**, the same underlying mechanism as Client Login, so there's only one auth pattern to build/maintain. Team members get a Supabase Auth account created manually (via the Supabase dashboard) for each person — Supabase's own user table is the "list of valid company members," no separate hand-rolled allowlist needed. They log in by requesting a magic link emailed to them.
    - Explicitly ruled out: SMS/phone codes (needs a paid third-party SMS provider, unnecessary cost/complexity for 1–3 users) and enterprise MFA/SSO like Duo (built for much larger orgs).
    - Optional future hardening: TOTP-based two-factor (e.g. Google Authenticator/Authy) as a second factor on top of the magic link, which Supabase supports natively at no extra cost — not required for launch, worth adding later if desired.
    - **v1 scope (decided):** once logged in, the admin area needs just two things to start:
      1. A **new client entry form** — captures name, email, phone number, and **project name** (real name or a code name, either is fine) — plus whatever else turns out to be needed.
      2. A **client list** — shows current clients, including each one's project name.
    - Everything else beyond what's specified here (editing/removing clients, richer content management, etc.) is intentionally deferred — add as needed once this basic version is in use.
    - **Team/personnel management (decided):** the admin area also needs a form for entering the people who'll appear on the About page — fields: name, photo, title (free text — see About page item above for the Builder vs. Advisor title conventions), section (**Builder** or **Advisor**), short bio, and LinkedIn URL. Saved to Supabase, same as client records; the About page's team section renders from this table rather than being hand-coded per person. Whether that render happens at build time (needs a new release/deploy whenever personnel changes, matching this site's release-based deploy model) or at request time (same pattern as the dynamic client-portal template above) is still open — see Open Questions.
    - **Submitting the new client form does four things (decided):**
      1. Writes the client's info to the database (Supabase).
      2. Generates the 6-character Client ID and returns it to the studio to relay to the client.
      3. Adds the new client to the client list on the Company/admin page.
      4. Creates that client's page under the Client Login area — headed with the **project name**, includes basic client info, and starts with placeholder text along the lines of "This is where we'll post information about your project" until real project content is added later. **Implementation (decided):** this is one dynamic client-portal template page keyed by Client ID, rendering each client's project name/info/content pulled from Supabase at request time — not a literal new static file generated per client. Fits the site's static-output-to-GitHub-Pages deployment model without needing a new release/deploy for every client signup.
