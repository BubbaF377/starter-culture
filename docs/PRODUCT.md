# StarterCulture

Working name: **StarterCulture** (styled as one word, no space). Brand/marketing website for StarterCulture, Christian's small AI-native software development studio, hosted at starterculturestudio.com.

## Working agreement

- Conversations about this project in the Claude desktop/Cowork app are planning-only: they get captured here as requirements, decisions, or open questions, not applied as direct code changes from that app.
- Actual code changes to this repo happen in Claude Code / VS Code sessions. An agent working from the desktop app should read this file for current context but not edit source files (e.g. anything under `src/`, `public/`, config files) unless Christian explicitly asks for that in the moment.

## Vision

A brand site that introduces StarterCulture as a small software development studio doing AI-first, AI-native development, and showcases the studio's products — starting with Devlore. The site should feel light, clean, and minimal, and give the studio a real home on the web that can grow to list future products, plus room for a company/team page and an eventual client portal.

10. **Client Login (`src/pages/client-login.astro`), Client Portal (`src/pages/client-portal.astro`), and Company Login (`src/pages/company-login.astro`)** — the login-gated flows for clients and for StarterCulture's own team. **The backend moved from Supabase to Firebase on 2026-09-26 (see "Backend" below).** The Firebase versions have been tested end-to-end locally against the deployed backend (2026-09-26; test data deleted afterward) but aren't live until the next release (item 12). The old `src/pages/_clients.astro` wireframe (non-functional email/password form) has been deleted — fully superseded by these pages.
    - **Nav/footer Login dropdown — built.** A single **"Login"** entry in both the header nav and footer opens a dropdown with two options, **"Client Login"** and **"Company Login"**. Implemented as a plain `<details>`/`<summary>` element (no JS framework) in `src/components/Header.astro` and `Footer.astro`, styled via `.login-dropdown`/`.login-menu` in `src/styles/site.css`; footer's copy of the menu opens upward so it stays on-screen. A small shared script in `src/layouts/Layout.astro` closes any open dropdown on an outside click.
    - **Client Login page.** Landing copy: "This page is for StarterCulture clients. Log in here to see working models, documentation, and other materials for your project." The Client ID form calls the `clientOtpRequest` callable Cloud Function, then reveals the passcode step; that form calls `clientOtpVerify`, which returns a Firebase custom token. The page signs in with it (`signInWithCustomToken`) and redirects to `/client-portal`. Errors (`not_found`/`expired`/`too_many_attempts`/`incorrect_code`/network failure) render inline via the shared `.form-error` style in `site.css`.
    - **Client Portal page (`client-portal.astro`).** Waits for Firebase Auth state, reads the `client_id` custom claim from the signed-in user's ID token, and reads that client's `clients/{clientId}` doc straight from Firestore (no server function in between — the Firestore rules do the gating). Renders `project_name`/`content`. Redirects back to Client Login if nobody's signed in as a client, or if Firestore denies the read (e.g. session older than 7 days). "Log out" signs out of Firebase Auth.
    - **Decided/implemented login flow:** (a) client enters their **Client ID** (an identifier StarterCulture issues per client — not their email); (b) on submit, we look up whether that ID exists in our client records; (c) if it exists, we email a one-time passcode to the email address on file for that client; (d) they're shown the passcode-entry step; (e) once the correct passcode is entered, they're authenticated and land on their client content area.
    - **Backend: Firebase (decided 2026-09-26), replacing Supabase.** Supabase's free tier pauses a project after about a week with no activity, which isn't acceptable for a site that can easily go that long without a login. Christian already works in the Google ecosystem and has another project on Firebase. Details:
      - Firebase project `starter-culture` (ID `starter-culture-d6b5f`), on the **Blaze** (pay-as-you-go) plan — required for Cloud Functions (and for Cloud Storage, which the personnel photo upload will need). Expected to stay within Blaze's free quotas at this site's scale; set a budget alert (alerts notify, they don't cap spend).
      - A dedicated project, not shared with Christian's other Firebase project — same reasoning as the earlier decision not to reuse `perfect-stranger`'s Supabase project (keeps each product's Auth users, email templates, and authorized domains separate).
      - Hosting stays on **GitHub Pages** (item 12) — Firebase is backend-only.
      - Client-side web config lives in `src/lib/firebase-config.ts`. The Firebase web API key is a public project identifier, not a secret — access control comes from Firestore rules and Auth, not from hiding it.
      - The old Supabase project (`starter-culture`, `wklchodmfgmtsateuryy.supabase.co`) was **deleted on 2026-09-26**, after the Firebase version passed an end-to-end test (staff sign-in → create client → passcode email via Resend → client portal), along with its `starter-culture-client-login` Resend key. The local `supabase/` directory (migrations + Edge Functions) has been removed from the repo; it remains in git history.
    - **Auth architecture (decided):** Clients authenticate with Client ID + a one-time passcode checked by a Cloud Function, which then mints a **Firebase custom token** (uid `client_<CLIENTID>`, custom claim `client_id`). Firebase manages the resulting session and token refresh, replacing the Supabase-era hand-rolled `client_sessions` table and `x-client-session` header. Consequence: clients now *do* appear as Firebase Auth users, so "signed in" no longer means "is staff." **Staff are identified by a `staff: true` custom claim** (decided over an allowlist collection in Firestore), granted per team member with the Admin SDK script `functions/scripts/set-staff.mjs`. Firestore rules check that claim, never mere sign-in.
    - **Client session length:** 7 days, enforced in `firestore.rules` by checking the ID token's `auth_time`. After that, the portal's read is denied and the client is sent back to log in again.
    - **Firestore data model** (rules in `firestore.rules`, deployed with `firebase deploy`):
      - `clients/{clientId}` — the doc ID *is* the 6-character Client ID. Fields: `name`, `email`, `phone`, `project_name`, `content` (starts as "This is where we'll post information about your project."), `created_at`. Rules: staff can read/create/update; a client can read only their own doc (their `client_id` claim matches the doc ID).
      - `client_otp_codes/{clientId}` — `code_hash` (SHA-256; the code is never stored raw), `expires_at`, `attempts`. No rule grants any access — only Cloud Functions touch it, via the Admin SDK, which bypasses rules.
      - `personnel/{id}` — the About page's Builders/Advisors (see item 9): `name`, `title`, `section` (`builder`/`advisor`), `bio`, `linkedin_url`, `photo_url`, `sort_order`, `created_at`. Rules: public read; staff-only write.
    - **Cloud Functions** (`functions/`, TypeScript, 2nd-gen callable functions, region `us-central1` — same as the Firestore database, whose location is permanent). Deployed from the repo with `firebase deploy`, so the local source *is* the deployed source — the Supabase-era hand-sync between local files and a dashboard editor is gone. Callable functions handle CORS themselves.
      - `clientOtpRequest` — takes `{ clientId }`; if it matches a client, generates a 6-digit passcode, stores its hash (replacing any prior code, 10-minute expiry), and emails it via Resend. Always returns the same `{ ok: true }` whether or not the ID existed, so it can't be used to enumerate valid Client IDs.
      - `clientOtpVerify` — takes `{ clientId, code }`; checks the hash, expiry, and attempt count (max 5) in a transaction; on success deletes the code and returns `{ ok: true, token }` with the custom token.
      - No portal-content function — the portal reads Firestore directly under the rules.
    - **Email delivery: Resend**, sending from `otp@mail.starterculturestudio.com` — a dedicated subdomain (not the root domain) so its SPF/DKIM/DMARC records don't touch the existing Porkbun email-forwarding setup for `dev@starterculturestudio.com`. Domain is **Verified**. The API key is stored as the Cloud Functions secret `RESEND_API_KEY` (Sending-access only). A new Resend key is needed for Firebase, since the Supabase secret can't be read back.
    - **Client ID generation (decided):** the Client ID isn't chosen by hand — when the studio creates a new client record (via the Company/admin area below), the site generates the ID itself and hands it back to us to relay to the client. **Format: a 6-character alphanumeric code**, kept simple since the client has to type it in. Collisions are handled: the admin page creates the doc in a Firestore transaction that fails if that ID already exists, and retries with a fresh ID (up to 5 times).
    - Behind the login, each client sees content StarterCulture uploads as work on their project progresses (e.g. working models, documentation) — exact content types and how the studio manages/uploads that content per client are still open (see below).
    - **Company Login page.** Copy: "StarterCulture team members: sign in with your email to reach the admin area." Uses Firebase Auth **email-link sign-in** (`sendSignInLinkToEmail`), always showing the generic "check your email" step so the form can't be used to probe for team emails. The link returns to `/company-login`, which completes `signInWithEmailLink` (asking for the email again if the link was opened on a different device/browser), then checks the `staff` claim: staff go to `/company-admin`; anyone else is signed out and shown a no-access message. Unlike Supabase's `create_user: false`, Firebase email-link sign-in creates an Auth user for any address that completes it — harmless, because nothing is readable without the `staff` claim. `starterculturestudio.com`, `www.starterculturestudio.com`, and `localhost` must be on Firebase Auth's authorized-domains list.
11. **Company login / admin area** — a separate authenticated area for StarterCulture itself (`src/pages/company-admin.astro`), reached via the "Company Login" option in the same Login dropdown as Client Login (see above). **v1 (new client form + client list) is built against Firebase; the personnel form isn't built yet.** The page redirects to Company Login unless the signed-in user has the `staff` claim.
    - **Auth mechanism (decided): Firebase Auth email-link sign-in** (see Company Login above). Each team member signs in once to create their Auth user, then gets `staff: true` granted via `functions/scripts/set-staff.mjs` — the set of users holding that claim is the "list of valid company members," no separate allowlist needed. (Originally decided as Supabase magic links; carried over to Firebase in the 2026-09-26 migration.)
    - Explicitly ruled out: SMS/phone codes (needs a paid third-party SMS provider, unnecessary cost/complexity for 1–3 users) and enterprise MFA/SSO like Duo (built for much larger orgs).
    - Optional future hardening: TOTP-based two-factor (e.g. Google Authenticator/Authy) as a second factor on top of the email link — Firebase supports TOTP MFA (requires the Identity Platform upgrade). Not required for launch.
    - **v1 scope (decided):** once logged in, the admin area needs just two things to start:
      1. A **new client entry form** — captures name, email, phone number, and **project name** (real name or a code name, either is fine) — plus whatever else turns out to be needed.
      2. A **client list** — shows current clients, including each one's project name.
    - Everything else beyond what's specified here (editing/removing clients, richer content management, etc.) is intentionally deferred — add as needed once this basic version is in use.
    - **Team/personnel management (decided):** the admin area also needs a form for entering the people who'll appear on the About page — fields: name, photo, title (free text — see About page item above for the Builder vs. Advisor title conventions), section (**Builder** or **Advisor**), short bio, and LinkedIn URL. Saved to Firestore (`personnel`), with photos in Cloud Storage for Firebase; the About page's team section renders from this collection rather than being hand-coded per person. Whether that render happens at build time (needs a new release/deploy whenever personnel changes, matching this site's release-based deploy model) or at request time (same pattern as the client portal) is still open — see Open Questions.
    - **Submitting the new client form does four things (decided):**
      1. Writes the client's info to the database (Firestore `clients`).
      2. Generates the 6-character Client ID and returns it to the studio to relay to the client.
      3. Adds the new client to the client list on the Company/admin page.
      4. Creates that client's page under the Client Login area — headed with the **project name**, includes basic client info, and starts with placeholder text along the lines of "This is where we'll post information about your project" until real project content is added later. **Implementation (decided):** this is one dynamic client-portal template page keyed by Client ID, rendering each client's project name/info/content pulled from Firestore at request time — not a literal new static file generated per client. Fits the site's static-output-to-GitHub-Pages deployment model without needing a new release/deploy for every client signup.
